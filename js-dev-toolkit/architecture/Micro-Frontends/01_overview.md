# 마이크로 프론트엔드 개요

## 문제: Frontend Monolith

```
백엔드는 MSA로 분리했는데...
                                         
[팀A: 주문] [팀B: 결제] [팀C: 회원]    → 백엔드: 서비스별 독립 배포
        ↓         ↓         ↓
    ┌────────────────────────────┐
    │     하나의 거대한 프론트엔드  │    → 프론트: 모든 팀이 하나에서 개발
    │  React App (모든 기능 포함)  │
    └────────────────────────────┘
                  │
    팀A 코드 배포 → 전체 재빌드·재배포
    팀B 버그 → 팀A, 팀C 기능도 영향
    팀간 CSS 충돌, 상태 충돌 빈번
```

---

## 해결: 마이크로 프론트엔드

> **비유**: 백화점에 브랜드 매장들이 입점.  
> 삼성 매장, 애플 매장, LG 매장은 각자 인테리어·직원·재고를 독립 관리.  
> 고객은 하나의 백화점을 경험하지만, 각 매장은 서로 간섭하지 않는다.

```
                ┌──────────────────────────────────┐
                │         Shell App (백화점)          │
                │   ┌─────────────────────────┐    │
                │   │       Header / Nav       │    │  ← Shell이 관리
                │   └─────────────────────────┘    │
                │   ┌────────┐┌───────┐┌────────┐  │
                │   │  주문   ││  결제  ││  회원   │  │  ← 각 팀 독립 관리
                │   │  MFE  ││  MFE  ││  MFE   │  │
                │   └────────┘└───────┘└────────┘  │
                └──────────────────────────────────┘

팀A → 주문 MFE만 빌드·배포 (다른 팀 무관)
팀B → 결제 MFE만 빌드·배포
```

---

## Monolith Frontend vs Micro Frontends

| 기준 | Monolith Frontend | Micro Frontends |
|---|---|---|
| 배포 | 전체 함께 | 팀별 독립 |
| 기술 스택 | 통일 | 팀별 자유 |
| 팀 자율성 | 낮음 | 높음 |
| 초기 설정 | 단순 | 복잡 |
| 번들 크기 | 하나의 큰 번들 | 분산 (lazy load) |
| CSS 격리 | 전역 충돌 위험 | 각 MFE 격리 |

## 언제 선택하는가?

```
팀이 여러 개이고 프론트엔드 배포 충돌이 잦은가?
  Yes → MFE 검토

각 기능 영역이 다른 속도로 릴리즈되어야 하는가?
  Yes → MFE 검토

소규모 팀, 단일 제품인가?
  Yes → 모놀리식 프론트엔드 유지
```

> **실무 채택**: IKEA, Zalando, Spotify — 대규모 다팀 조직에서 주로 사용.
