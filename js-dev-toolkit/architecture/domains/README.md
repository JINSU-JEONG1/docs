## 이 분류를 사용하는 방법

`domains/`는 설계 대상에 따라 문서를 나눈 목록입니다. 여기서 도메인은 주문·결제 같은 업무 영역이 아니라 **애플리케이션·데이터·연계·인프라·보안이라는 기술 영역**을 뜻합니다.

하나의 시스템을 설계할 때 여러 영역을 함께 검토합니다. 전체 요구와 구성요소의 관계는 [솔루션 아키텍처](../solution/README.md)에서 정리하고, 각 영역의 상세 결정은 아래 폴더에서 찾아봅니다.

## 여러 영역을 함께 검토하는 예

다음은 주문 기능을 설계할 때 이 분류를 사용하는 예시입니다. 실제 구현이나 확정된 설계를 나타내지는 않습니다.

1. **애플리케이션:** 주문·결제·재고의 책임과 모듈 또는 서비스 경계를 정리합니다.
2. **데이터:** 주문 상태의 원본, 변경 권한과 일관성 요구를 정리합니다.
3. **연계:** 결제 요청과 재고 변경의 계약, 실패 시 재시도·보상 흐름을 검토합니다.
4. **인프라:** 배포 위치, 장애 감지, 복구 절차와 필요한 자원을 검토합니다.
5. **보안:** 각 단계의 사용자·서비스 권한, 보호할 데이터와 감사 기록을 검토합니다.

이 순서는 문서를 탐색하기 위한 예시입니다. 보안·운영 요구가 다른 설계에 영향을 주므로 실제 검토에서는 각 영역을 오가며 조정합니다.

## 헷갈리기 쉬운 분류

| 주제 | 주된 위치 | 구분 기준 |
|---|---|---|
| MSA와 내부 코드 구조 | application | 서비스 분리와 내부 의존성은 서로 다른 수준의 결정입니다. |
| Event-Driven | integration | 시스템 사이의 이벤트 전달과 처리 흐름을 다룹니다. |
| CQRS와 Event Sourcing | data | 조회·명령 분리 및 상태를 기록·재구성하는 방식을 다룹니다. |
| 네트워크 구성과 접근 정책 | infrastructure / security | 연결 경로는 인프라, 허용할 통신과 검증 기준은 보안을 중심으로 작성합니다. |
| DDD·C4·ADR | [practice](../practice/README.md) | 설계 대상이 아니라 탐색·표현·기록 방법으로 분류합니다. |

중복되는 주제는 중심 문서 한 곳에서 설명하고 관련 영역에서 링크로 연결합니다. 서로 다른 폴더에 같은 본문을 복사해 두지 않습니다.

## 현재 작성 상태

애플리케이션 영역에는 대표 문서인 [계층형 구조](<application/application-structure/[draft]01-layered.md>)와 MSA, Modular Monolith, Hexagonal / Clean, Micro-Frontends의 본문이 있습니다. 데이터 영역에는 [데이터 모델링과 소유권](<data/[draft]01-modeling-and-ownership.md>), 연계 영역에는 Event-Driven 본문이 있습니다.

솔루션의 [전체 흐름 설계](<../solution/[draft]03-end-to-end-design.md>)부터 계층형 구조와 데이터 모델링을 이어 읽으면 같은 주문 예제로 영역 간 관계를 이해할 수 있습니다. 나머지 새 주제 파일은 작성 예정이며 각 영역 README에 범위를 표시했습니다.
