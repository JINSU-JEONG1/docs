# MSA 개요

## MSA란?

Microservices Architecture. 하나의 애플리케이션을 **독립적으로 배포 가능한 작은 서비스들**의 집합으로 구성하는 아키텍처 패턴.

- 서비스별 단일 비즈니스 기능 담당
- 서비스별 독립 개발 / 배포 / 확장
- 서비스별 자체 DB 소유 (DB per Service)
- 네트워크(API, 메시지)로 서비스 간 통신

---

## Monolith vs MSA

### Monolith

```
[ 단일 애플리케이션 ]
  ├── 사용자 모듈
  ├── 주문 모듈
  ├── 상품 모듈
  └── 결제 모듈
       └── 공유 DB
```

| 장점 | 단점 |
|---|---|
| 개발/배포 단순 | 작은 변경도 전체 재배포 |
| 함수 호출 → 빠름 | 특정 모듈만 스케일 불가 |
| 트랜잭션 처리 쉬움 | 팀 규모 커지면 충돌 빈번 |

### MSA

```
     [ API Gateway ]
            │
  ┌─────────┼─────────┐
  │         │         │
[User]   [Order]  [Payment]
  │         │         │
[DB]      [DB]      [DB]
```

| 장점 | 단점 |
|---|---|
| 서비스별 독립 배포 | 분산 시스템 복잡성 |
| 서비스별 스케일 아웃 | 분산 트랜잭션 어려움 |
| 기술 스택 자유 (폴리글랏) | 운영 인프라 비용 증가 |
| 장애 격리 | 서비스 간 데이터 중복 |

---

## 언제 MSA를 선택하는가?

| 상황 | 권장 |
|---|---|
| 팀 소규모, 초기 단계 | Monolith |
| 도메인 경계가 명확히 분리됨 | MSA 검토 |
| 특정 모듈에 트래픽 집중 | MSA (해당 서비스만 스케일) |
| 여러 팀이 독립 배포해야 함 | MSA |

> **Monolith First (Martin Fowler)** — 처음엔 모놀리식으로 시작, 경계가 명확해지면 분리

---

## MSA 핵심 특성

| 특성 | 설명 |
|---|---|
| 단일 책임 | 서비스 하나 = 비즈니스 역할 하나 |
| 자율성 | 다른 서비스 재배포 없이 독립 배포 |
| 느슨한 결합 | 인터페이스(API)로만 통신, 내부 구현 비공개 |
| 높은 응집도 | 관련 기능은 같은 서비스 안에 |
| 분산 데이터 | 서비스마다 자체 DB, 공유 DB 금지 |
