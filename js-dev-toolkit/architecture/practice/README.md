## 이 영역에서 다루는 것

설계 대상 자체가 아니라 설계를 찾아내고 표현하고 검증하며 개선하는 방법을 다룹니다. 업무를 이해하는 활동부터 결정 기록, 구조 검토, 기술 부채 관리까지 설계 작업의 흐름에 따라 찾아볼 수 있습니다.

- **핵심 질문:** 설계의 근거를 어떻게 찾고, 다른 사람에게 설명하며, 구현 후에도 지켜지는지 확인할 것인가?
- **정리할 산출물:** 업무 모델, 아키텍처 다이어그램, 설계 결정 기록, 검토 결과, 개선 목록입니다.

## 읽는 순서와 활용 방법

1. DDD와 EventStorming 항목에서 업무 언어와 경계를 탐색할 범위를 확인합니다.
2. C4로 설명할 수준을 나누고, ADR에 문제·대안·결정·결과를 기록합니다.
3. 아키텍처 검토와 자동 점검으로 위험을 확인하고, 남은 개선 항목을 기술 부채로 관리합니다.

위 순서는 본문을 작성하거나 설계를 진행할 때의 순서입니다. 현재 학습 가능한 상세 문서는 [전체 안내의 바로 읽을 수 있는 문서](../README.md#바로-읽을-수-있는-문서)에서 확인할 수 있습니다.

## 다른 영역과의 경계

DDD와 EventStorming은 설계를 탐색하는 방법, C4는 구조를 표현하는 방법, ADR은 결정을 기록하는 방식으로 분류합니다. MSA 같은 시스템 구조와 나란히 비교하는 대안으로 취급하지 않습니다.

## 문서 작성 기준

각 본문에는 문제와 적용 조건, 핵심 구조, 예시, 장단점, 운영 시 확인할 사항, 근거 자료를 순서대로 정리합니다. 특정 선택을 권장할 때에는 전제와 제약을 함께 적습니다.

작성 예정 파일에 본문을 채우면 이 표의 상태를 갱신합니다. 파일의 단계 접두사를 변경하면 [전체 안내](../README.md)와 이 문서에서 해당 파일을 가리키는 링크도 함께 수정합니다.
