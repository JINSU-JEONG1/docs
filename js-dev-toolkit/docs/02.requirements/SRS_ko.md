## 1. 개요

### 1.1 문서 목적

> 이 SRS가 왜 작성되었는지, 누가 읽는 문서인지를 기술한다.

이 문서는 \[프로젝트명\] 시스템의 소프트웨어 요구사항을 명세하기 위해 작성되었다.
본 문서는 발주자, 프로젝트 관리자, 시스템 분석가, 개발자, QA 엔지니어가 공통 기준으로 활용하며,
이후 작성되는 설계서 및 테스트 케이스의 기준 문서로 사용된다.

---

### 1.2 프로젝트 범위

> 시스템이 무엇을 하는지(In-Scope)와 무엇을 하지 않는지(Out-of-Scope)를 명확히 구분한다.
> "안 하는 것"을 명시하지 않으면 나중에 분쟁의 씨앗이 된다.

**In-Scope (포함 범위)**
- 모바일 앱(iOS/Android) 회원가입 및 로그인 기능
- 상품 조회, 장바구니, 주문 및 결제 기능
- 마이페이지 주문 내역 조회

**Out-of-Scope (제외 범위)**
- 관리자 백오피스 웹 시스템 (별도 프로젝트로 진행)
- 정산 및 세금계산서 발행 기능
- 해외 결제 및 다국어 지원

---

### 1.3 용어 및 약어 정의

> 문서 전체에서 사용하는 용어를 통일한다. 개발자와 기획자가 같은 단어를 다른 의미로 쓰는 것을 방지한다.

| 용어 / 약어 | 정의 |
|---|---|
| SRS | Software Requirements Specification. 소프트웨어 요구사항 명세서 |
| REQ | Requirement. 요구사항 식별자 접두어 |
| PG | Payment Gateway. 결제 대행사 모듈 |
| JWT | JSON Web Token. 인증 토큰 방식 |
| UAT | User Acceptance Test. 사용자 인수 테스트 |
| 재고 시스템 | 사내 ERP 내 재고 관리 모듈을 지칭 |

---

### 1.4 참조 문서

> 이 SRS 작성에 사용된 상위 문서, 계약서, 표준 등을 열거한다.

| 문서명 | 버전 | 작성일 | 비고 |
|---|---|---|---|
| 제안요청서 (RFP) | v1.2 | YYYY-MM-DD | 발주사 제공 |
| 사업수행계획서 | v1.0 | YYYY-MM-DD | |
| 화면 설계서 (Wireframe) | v0.3 | YYYY-MM-DD | 초안, 변경 가능 |
| IEEE 830-1998 | - | - | SRS 작성 표준 참조 |

---

### 1.5 문서 버전 이력

> 변경 이력을 관리한다. 누가 언제 무엇을 바꿨는지 추적 가능해야 한다.

| 버전 | 날짜 | 작성자 | 변경 내용 |
|---|---|---|---|
| v0.1 | YYYY-MM-DD | 홍길동 | 초안 작성 |
| v0.2 | YYYY-MM-DD | 홍길동 | 3.2절 주문 모듈 요구사항 추가 |
| v1.0 | YYYY-MM-DD | 홍길동 | 검토 반영 후 승인본 확정 |

## 2. 전체 설명

### 2.1 제품 개요

> 시스템이 더 큰 그림에서 어디에 위치하는지, 어떤 외부 시스템과 연결되는지를 기술한다.
> 컨텍스트 다이어그램(Context Diagram)이 있으면 첨부한다.

\[프로젝트명\] 시스템은 \[회사명\]의 모바일 커머스 플랫폼으로,
iOS 및 Android 앱 클라이언트와 RESTful API 서버로 구성된다.
외부 시스템으로는 카카오 소셜 로그인 API, PG사(이니시스) 결제 모듈,
사내 ERP 재고 시스템과 연동된다.

```
[사용자 (iOS/Android 앱)]
        │
        ▼
[API 서버 (Spring Boot)]
        │
   ┌────┼────┐
   │    │    │
[카카오] [PG사] [ERP 재고]
```

---

### 2.2 제품 기능 요약

> 3장의 상세 내용에 들어가기 전, 주요 기능을 한눈에 파악할 수 있도록 요약한다.

| 기능 그룹 | 주요 기능 |
|---|---|
| 회원 관리 | 카카오 소셜 로그인, 생체 인증, 회원 정보 수정, 탈퇴 |
| 상품 | 상품 목록 조회, 상세 조회, 검색 및 필터링 |
| 주문/결제 | 장바구니, 주문 생성, PG 결제, 주문 취소/환불 |
| 마이페이지 | 주문 내역 조회, 배송 조회, 포인트 내역 |

---

### 2.3 사용자 유형 및 특성

> 시스템을 사용하는 사용자 유형별 특성과 권한 수준을 정의한다.

| 사용자 유형 | 설명 | 기술 수준 | 주요 사용 기능 |
|---|---|---|---|
| 일반 회원 | 앱을 통해 상품을 구매하는 최종 사용자 | 낮음 (스마트폰 기본 사용 가능) | 상품 조회, 주문, 결제 |
| 비회원 | 로그인 없이 앱을 탐색하는 사용자 | 낮음 | 상품 조회만 가능 |
| 시스템 관리자 | 백오피스를 통해 상품·주문을 관리 | 높음 | 전체 기능 (Out-of-Scope) |

---

### 2.4 운영 환경

> 시스템이 실행되는 하드웨어, OS, 네트워크 환경을 정의한다.

**클라이언트**
- iOS 16.0 이상 / Android 12.0 이상
- 네트워크: 4G/5G LTE, Wi-Fi 지원

**서버**
- OS: Ubuntu 22.04 LTS
- 런타임: JDK 17 (Spring Boot 3.x)
- DB: MySQL 8.0 (AWS RDS)
- 인프라: AWS (ECS + ALB)

---

### 2.5 설계 및 구현 제약사항

> 기술적·법적·정책적으로 반드시 따라야 하는 제약을 기술한다.
> "어떻게 만들어야 한다"가 아니라 "어떤 제약 안에서 만들어야 한다"를 적는다.

- 개인정보보호법에 따라 사용자 개인정보(이름, 연락처)는 암호화하여 저장해야 한다.
- 결제 처리는 PCI-DSS 인증을 보유한 PG사(이니시스)를 통해서만 이루어져야 한다.
- 앱 스토어(Apple, Google) 심사 정책을 준수해야 한다.
- 공공 API(카카오 로그인)는 해당 플랫폼의 약관 및 정책을 준수해야 한다.

---

### 2.6 가정 및 의존성

> 이 SRS가 참으로 가정하는 전제 조건과, 외부 시스템·환경에 대한 의존성을 기술한다.
> 가정이 깨지면 요구사항도 재검토가 필요하다.

**가정**
- 카카오 로그인 API는 프로젝트 기간 내 안정적으로 운영된다고 가정한다.
- 사용자는 인터넷 연결 환경에서 앱을 사용한다고 가정한다.

**의존성**
- PG사(이니시스) 계약 및 테스트 환경 제공이 개발 착수 전에 완료되어야 한다.
- ERP 재고 시스템의 API 명세는 설계 단계 착수 전 확정되어야 한다.

## 3. 기능적 요구사항

> **요구사항 ID 규칙:** `REQ-[모듈코드]-[순번]`
> 예) REQ-AUT-001, REQ-ORD-002
>
> **우선순위 기준:**
> - High: 서비스 출시를 위해 반드시 구현되어야 하는 기능
> - Medium: 출시 후 1차 업데이트 내 구현 목표
> - Low: 향후 검토
>
> **작성 원칙:**
> - 처리 로직에는 시스템 동작만 기술한다 (UI 동작 기술 금지)
> - 모든 요구사항은 검증 가능(Verifiable)하고 추적 가능(Traceable)해야 한다
> - 각 요구사항은 단 하나의 의미만 가져야 한다 (중의적 표현 금지)

---

### 3.1 [모듈명 예시] 회원 관리 (Module: AUTH)

#### REQ-AUT-001: 카카오 소셜 로그인

| 항목 | 내용 |
|---|---|
| **설명** | 사용자는 카카오 인증을 통해 회원가입 및 로그인을 수행할 수 있어야 한다. |
| **입력** | 카카오 OAuth 인증 토큰, 사용자 동의 항목(이메일, 닉네임) |
| **처리 로직** | 1. 시스템은 전달받은 카카오 토큰의 유효성을 검증한다. <br>2. 토큰 검증 성공 시, 카카오 고유 ID로 기존 회원 여부를 조회한다. <br>3. 신규 회원인 경우: 회원 테이블에 신규 레코드를 생성하고 JWT를 발급한다. <br>4. 기존 회원인 경우: 즉시 JWT를 발급한다. <br>5. 토큰 검증 실패 시: 에러 코드 401과 함께 실패 응답을 반환한다. |
| **출력** | JWT 액세스 토큰(유효기간 1시간), 리프레시 토큰(유효기간 30일) |
| **예외 처리** | 카카오 API 서버 장애 시 사용자에게 "잠시 후 다시 시도해주세요" 안내 메시지를 반환한다. |
| **우선순위** | High |
| **수용 여부** | Y |
| **관련 요구사항** | REQ-AUT-002 (생체 인증은 이 요구사항의 로그인 성공 이후 등록 가능) |

---

#### REQ-AUT-002: 생체 인증 등록 및 해제

| 항목 | 내용 |
|---|---|
| **설명** | 로그인한 회원은 디바이스 생체 정보(지문/Face ID)를 이용한 간편 로그인을 활성화하거나 비활성화할 수 있어야 한다. |
| **입력** | 회원 ID, 생체 인증 활성화/비활성화 요청 값 |
| **처리 로직** | 1. 활성화 요청 시: 시스템은 디바이스 OS에 생체 인증 등록을 위임하고, 성공 시 해당 회원의 생체 인증 플래그를 활성(Y)으로 저장한다. <br>2. 비활성화 요청 시: 해당 회원의 생체 인증 플래그를 비활성(N)으로 저장하고 등록된 생체 정보 연결을 해제한다. <br>3. 디바이스가 생체 인증을 지원하지 않을 경우: 에러 코드와 함께 지원 불가 응답을 반환한다. |
| **출력** | 처리 결과 성공/실패 응답 코드 |
| **예외 처리** | 생체 인증 3회 연속 실패 시 해당 기능을 잠금 처리하고 비밀번호 재인증을 요구한다. |
| **우선순위** | Medium |
| **수용 여부** | Y |
| **관련 요구사항** | REQ-AUT-001 |

### 3.2 [모듈명 예시] 주문 및 결제 (Module: ORDER)

#### REQ-ORD-001: 장바구니 상품 결제 요청

| 항목 | 내용 |
|---|---|
| **설명** | 사용자는 장바구니에 담긴 상품의 수량을 변경하거나 선택하여 결제를 요청할 수 있어야 한다. |
| **입력** | 사용자 ID, 선택된 상품 ID 목록, 각 상품별 수량 |
| **처리 로직** | 1. 시스템은 선택된 상품의 현재 실재고를 재고 시스템에 조회한다. <br>2. 주문 수량이 실재고보다 많을 경우: 에러 코드와 함께 결제 진입을 차단한다. <br>3. 재고가 충분한 경우: 상품 금액 합계와 배송비를 합산하여 결제 금액을 산출한다. <br>4. 산출된 금액으로 PG 연동 모듈에 결제 요청을 전달한다. |
| **출력** | 결제 요청 성공 시 주문번호, 결제 실패 시 실패 사유 코드 |
| **예외 처리** | PG사 응답 지연(10초 초과) 시 타임아웃 처리하고 주문 상태를 '결제 미확인'으로 저장한다. |
| **우선순위** | High |
| **수용 여부** | Y |
| **관련 요구사항** | REQ-ORD-002 (결제 완료 후 주문 확인 알림) |

## 5. 외부 인터페이스 요구사항

### 5.1 사용자 인터페이스

> 화면의 상세 디자인은 화면설계서(스토리보드)에 기술한다.
> 이 항목에는 UI에 대한 시스템 수준의 제약 조건만 기술한다.

- 앱은 iOS Human Interface Guidelines 및 Android Material Design 가이드라인을 준수해야 한다.
- 시스템 점검 또는 오류 발생 시, 사용자에게 적절한 안내 메시지를 표시해야 한다.

---

### 5.2 하드웨어 인터페이스

- 앱은 디바이스의 카메라(QR 스캔), 생체 인증 센서(Touch ID / Face ID)에 접근할 수 있어야 한다.
- 위 하드웨어가 없는 디바이스에서는 해당 기능이 비활성화되며 대체 수단을 제공해야 한다.

---

### 5.3 소프트웨어 인터페이스

| 연동 시스템 | 인터페이스 방식 | 목적 | 비고 |
|---|---|---|---|
| 카카오 로그인 API | REST API (OAuth 2.0) | 소셜 로그인 인증 | 카카오 개발자 문서 참조 |
| 이니시스 PG | REST API | 결제 처리 | 별도 계약 필요 |
| 사내 ERP (재고) | REST API | 실재고 조회 | API 명세 수신 예정 |
| FCM (Firebase) | REST API | 푸시 알림 발송 | |

---

### 5.4 통신 인터페이스

- 모든 API 통신은 HTTPS (TLS 1.3) 프로토콜을 사용한다.
- API 데이터 포맷은 JSON을 표준으로 사용한다.
- API 버전 관리는 URI 방식(`/api/v1/...`)을 따른다.

## 6. 요구사항 추적 매트릭스 (RTM)

> RTM은 요구사항이 설계·구현·테스트 단계에서 누락되지 않았음을 보장한다.
> 요구사항 ID와 설계서 항목, 테스트 케이스 ID를 연결하여 관리한다.
> 초기 SRS 작성 시에는 요구사항 ID와 출처(RFP 항목)만 채우고, 이후 단계에서 점진적으로 채워나간다.

| 요구사항 ID | 요구사항 요약 | 출처 (RFP 항목) | 화면설계서 | API 명세 | 테스트 케이스 ID | 구현 여부 |
|---|---|---|---|---|---|---|
| REQ-AUT-001 | 카카오 소셜 로그인 | RFP-3.1 | UI-LOGIN-001 | API-AUTH-001 | TC-AUT-001 | - |
| REQ-AUT-002 | 생체 인증 등록/해제 | RFP-3.2 | UI-MYPAGE-003 | API-AUTH-002 | TC-AUT-002 | - |
| REQ-ORD-001 | 장바구니 결제 요청 | RFP-4.1 | UI-ORDER-001 | API-ORD-001 | TC-ORD-001 | - |
| REQ-PER-001 | 상품 목록 API 응답속도 | RFP-6.1 | - | API-PRD-001 | TC-PER-001 | - |
| REQ-SEC-001 | TLS 1.3 통신 암호화 | RFP-6.3 | - | - | TC-SEC-001 | - |
