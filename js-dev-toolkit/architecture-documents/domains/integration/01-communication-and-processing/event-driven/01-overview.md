# 이벤트 드리븐 아키텍처 개요

## 비유: 라디오 방송국

```
일반 아키텍처 (전화 통화 방식)         이벤트 드리븐 (라디오 방송 방식)
                                        
[주문 서비스] ──전화→ [결제 서비스]      [주문 서비스] ──📡 전파 송출──▶
[주문 서비스] ──전화→ [알림 서비스]                              
[주문 서비스] ──전화→ [재고 서비스]      [결제 서비스] ──📻 수신
                                        [알림 서비스] ──📻 수신
→ 주문 서비스가 수신자를 직접 알아야 함  [재고 서비스] ──📻 수신
→ 서비스 추가하면 주문 서비스 코드 수정  
                                        → 주문 서비스는 누가 수신하는지 모름
                                        → 서비스 추가해도 주문 코드 무변경
```

---

## 이벤트란?

> **이벤트 = 과거에 일어난 사실**. 변경 불가, 취소 불가.

```
명령 (Command)           이벤트 (Event)
───────────────          ───────────────
"결제를 처리해라"          "결제가 완료됐다"
미래형, 지시               과거형, 사실
수신자가 거절 가능          이미 일어난 일
```

```typescript
// 명령 → 직접 호출
paymentService.processPayment(orderId)

// 이벤트 → 발행 (누가 처리할지 모름)
eventBus.publish('order.created', { orderId, amount })
```

## Pub/Sub 구조

```
                    ┌─────────────────────────┐
                    │       Message Broker      │
[주문 서비스]        │  ┌──────────────────┐   │
  │                 │  │  order.created   │   │──→ [결제 서비스]
  │─ publish ──────▶│  │  (이벤트 채널)    │   │──→ [알림 서비스]
  │  "order.created"│  └──────────────────┘   │──→ [재고 서비스]
                    └─────────────────────────┘
```

- **Publisher (발행자)**: 이벤트 발생 사실만 브로커에 전달
- **Broker**: 이벤트 저장 및 라우팅 (Kafka, RabbitMQ)
- **Subscriber (구독자)**: 관심 있는 이벤트만 수신해서 처리

## 동기 vs 이벤트 드리븐 비교

| 기준 | 동기 호출 | 이벤트 드리븐 |
|---|---|---|
| 결합도 | 높음 (호출 대상을 직접 알아야 함) | 낮음 (브로커만 알면 됨) |
| 응답 | 즉시 | 나중에 (최종 일관성) |
| 장애 격리 | 수신 서비스 장애 → 발신 서비스도 영향 | 브로커가 버퍼링, 격리됨 |
| 확장성 | 수신자 추가 시 발신 코드 수정 | 수신자 추가해도 발신 무변경 |
| 디버깅 | 스택 트레이스 추적 쉬움 | 이벤트 흐름 추적 어려움 |

## 적합한 사용 사례

```
✅ 이벤트 드리븐이 좋은 경우
- 주문 완료 후 → 결제, 알림, 재고 차감, 포인트 적립 동시 처리
- 여러 서비스가 같은 이벤트에 반응해야 할 때
- 처리 결과를 즉시 받을 필요 없을 때

❌ 동기 호출이 더 나은 경우
- "재고가 있나요?" → 즉시 응답 필요
- 결과값이 다음 요청에 필요한 경우
- 트랜잭션 경계가 명확해야 하는 경우
```
