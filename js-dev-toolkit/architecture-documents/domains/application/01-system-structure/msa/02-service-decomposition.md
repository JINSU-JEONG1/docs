# 서비스 분해 (Service Decomposition)

## 핵심 질문: 서비스를 어떻게 나누는가?

서비스 분해는 MSA에서 가장 어렵고 중요한 결정.  
잘못 나누면 오히려 Monolith보다 복잡해진다.

---

## 분해 전략

### 1. 비즈니스 기능 기준 (Business Capability)

조직이 수행하는 비즈니스 기능 단위로 분리.

```
이커머스 예시
├── 상품 관리 서비스    (상품 등록, 수정, 재고)
├── 주문 서비스        (주문 생성, 취소)
├── 결제 서비스        (결제 처리, 환불)
├── 배송 서비스        (배송 추적, 상태 업데이트)
└── 회원 서비스        (회원가입, 인증, 프로필)
```

### 2. DDD Bounded Context (도메인 경계)

도메인 모델의 경계를 기준으로 분리.  
같은 단어가 컨텍스트마다 다른 의미를 가질 때 경계가 생긴다.

```
"고객(Customer)"의 의미
├── 주문 컨텍스트  → 주문자 (이름, 배송지)
├── 결제 컨텍스트  → 납부자 (카드 정보, 청구지)
└── 마케팅 컨텍스트 → 타겟 (구매 이력, 선호도)
```

→ 컨텍스트마다 모델이 다르면 → 서비스로 분리

### 3. 변경 빈도 기준

변경 빈도가 다른 부분은 분리.

- 자주 바뀌는 것: 추천 알고리즘, 프로모션 → 별도 서비스
- 안정적인 것: 결제, 인증 → 분리해서 안정성 확보

---

## 서비스 크기 기준 (휴리스틱)

| 기준 | 설명 |
|---|---|
| 2 Pizza Rule | 팀원 2판 피자로 먹을 수 있는 규모 (6~8명) |
| 단일 배포 단위 | 하나의 서비스 = 독립적으로 배포 가능 |
| DB 독립성 | 다른 서비스 DB를 직접 조회하지 않아도 되는 단위 |

## 나쁜 분해 패턴

### Nano Service (지나치게 잘게 쪼갬)

```
❌ 안 좋은 예
- 이름 서비스 / 이메일 서비스 / 전화번호 서비스
→ 네트워크 오버헤드 > 이점
```

### 데이터 기반 분해 (DB 테이블 = 서비스)

```
❌ 안 좋은 예
- users 테이블 → User 서비스
- orders 테이블 → Order 서비스
→ 비즈니스 로직이 아닌 데이터 구조 기반 분리는 결국 tight coupling
```

---

## Anti-pattern: Distributed Monolith

서비스는 나눴지만 실제로는 강결합 상태.

```
증상
- 서비스 A 배포하려면 서비스 B도 함께 배포해야 함
- 서비스 간 동기 호출 체인이 깊음 (A → B → C → D)
- 공유 DB 또는 공유 라이브러리에 비즈니스 로직 존재
```

→ 가장 나쁜 결과: 분산 시스템 복잡성 + 모놀리식 결합도 동시에 가짐
