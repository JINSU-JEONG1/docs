# 장애 복원성 (Resilience)

분산 시스템에서 서비스 간 네트워크 호출은 언제든 실패할 수 있다.  
한 서비스의 장애가 전체로 퍼지는 것을 막는 패턴들.

---

## Circuit Breaker (서킷 브레이커)

전기 회로 차단기처럼, 장애 서비스로의 호출을 자동으로 차단.

```
상태 전이

[Closed] → 정상 호출
  │ 오류율 임계값 초과
  ▼
[Open] → 즉시 실패 반환 (호출 안 함) — 장애 서비스 보호
  │ 일정 시간 후
  ▼
[Half-Open] → 소수 요청만 허용해서 복구 여부 확인
  │ 성공 → [Closed]
  └ 실패 → [Open]
```

**효과**: 장애 서비스가 회복할 시간을 주고, 호출 스택 전체가 블로킹되는 것 방지

대표 라이브러리: Resilience4j (Java), Polly (.NET), opossum (Node.js)

---

## Retry (재시도)

일시적 네트워크 오류에 자동으로 재시도.

```
주의: 재시도는 멱등성(Idempotency)이 보장될 때만 안전
- GET, PUT → 멱등 → 재시도 가능
- POST (주문 생성) → 멱등 아님 → 중복 주문 위험
  → 클라이언트 고유 ID(Idempotency Key) 함께 전송
```

**Exponential Backoff + Jitter**
```
1차 재시도: 1초 후
2차 재시도: 2초 후
3차 재시도: 4초 후
+ Jitter(랜덤 편차): 여러 클라이언트가 동시에 재시도해서 서버 과부하 방지
```

---

## Timeout

응답을 무한정 기다리지 않음.

```
[Service A] → [Service B] (느림)
              ↑
        3초 내 응답 없으면 타임아웃 → 빠른 실패 반환
```

타임아웃 없이 → 스레드 점유 → 스레드 풀 고갈 → 서비스 A 전체 마비

---

## Bulkhead (벌크헤드)

선박의 격벽처럼, 서비스별로 스레드 풀/리소스 풀을 격리.

```
기존: 공유 스레드 풀
[Service A 호출] ─┐
[Service B 호출] ─┤→ [공유 스레드 풀 200개]
[Service C 호출] ─┘
→ Service C 느려지면 스레드 전부 점유 → A, B도 영향

Bulkhead 적용:
[Service A 호출] → [전용 스레드 풀 50개]
[Service B 호출] → [전용 스레드 풀 50개]
[Service C 호출] → [전용 스레드 풀 50개]
→ C가 느려져도 A, B는 영향 없음
```

---

## Fallback (폴백)

호출 실패 시 대체 응답 제공.

```
상품 추천 서비스 호출 실패
→ Fallback: 기본 베스트셀러 목록 반환 (캐시 or 하드코딩)
→ 완전 실패보다 낮은 품질이지만 서비스는 유지
```

---

## 패턴 조합 (Best Practice)

```
외부 서비스 호출 시 권장 순서:

1. Bulkhead  — 리소스 격리
2. Circuit Breaker — 장애 서비스 차단
3. Timeout — 응답 대기 시간 제한
4. Retry + Backoff — 일시적 오류 재시도
5. Fallback — 최종 실패 시 대체 응답
```

---

## Rate Limiting (속도 제한)

클라이언트가 과도한 요청을 보내는 것을 제한.

```
API Gateway 레벨에서 처리
- 사용자별: 초당 100 요청
- IP별: 분당 1000 요청
초과 시 429 Too Many Requests 반환
```
