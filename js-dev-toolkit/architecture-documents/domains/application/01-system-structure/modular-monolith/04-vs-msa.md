# 모듈러 모놀리스 vs MSA / MSA 이전 전략

## 언제 MSA로 전환하는가?

모듈러 모놀리스가 잘 설계되어 있다면, MSA 전환은 **기술적 결정이 아닌 조직적 결정**이다.

```
MSA 전환이 필요한 신호
├── 특정 모듈만 트래픽이 폭증 → 해당 서비스만 스케일 필요
├── 팀이 커져 배포 충돌이 잦아짐 → 독립 배포 필요
├── 특정 모듈에 다른 기술 스택이 필요 → 폴리글랏
└── 조직이 Conway's Law에 따라 서비스 경계를 그어야 함
```

> **Conway's Law**: 시스템 구조는 조직 커뮤니케이션 구조를 닮는다.  
> 팀이 나뉘면 자연스럽게 서비스도 나뉜다.

## Strangler Fig 패턴 (점진적 MSA 전환)

> 비유: 무화과나무(Strangler Fig)는 숙주 나무를 감싸며 자라다가,  
> 결국 숙주를 대체한다. 숙주는 서서히 사라진다.

```
1단계: 모놀리스 전체 운영 중
┌─────────────────────────┐
│     Monolith             │
│  [주문] [결제] [회원]    │
└─────────────────────────┘

2단계: 신규 기능은 새 서비스로
┌─────────────────────────┐     ┌──────────────┐
│     Monolith             │     │ 새 추천 서비스 │
│  [주문] [결제] [회원]    │     └──────────────┘
└─────────────────────────┘

3단계: 기존 기능 점진적 추출
┌─────────────────────────┐     ┌──────────────┐
│     Monolith             │     │ 추천 서비스   │
│  [결제] [회원]           │ +   ├──────────────┤
│                          │     │ 주문 서비스   │
└─────────────────────────┘     └──────────────┘

4단계: 모놀리스 소멸
┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│ 추천 서비스│ │ 주문 서비스│ │ 결제 서비스│ │ 회원 서비스│
└──────────┘ └──────────┘ └──────────┘ └──────────┘
```

## 모듈러 모놀리스가 MSA 전환을 쉽게 만드는 이유

| 조건 | 모듈러 모놀리스 | 일반 모놀리스 |
|---|---|---|
| 경계 명확성 | 이미 존재 → 서비스로 분리만 하면 됨 | 경계부터 찾아야 함 |
| 인터페이스 | 이미 정의됨 → API로 전환 용이 | 내부 호출 파악 후 API화 필요 |
| 테스트 | 모듈 단위 테스트 존재 | 전체 통합 테스트만 있는 경우 많음 |

> 모듈러 모놀리스를 잘 만든다 = MSA의 구조적 이점을 미리 갖춰두는 것.
