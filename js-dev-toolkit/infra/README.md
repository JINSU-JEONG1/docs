# Infra Templates

마이크로서비스 아키텍처(MSA) 환경의 일관된 구축 및 운영을 위한 인프라 코드(IaC) 및 설정 템플릿 모음입니다.

---

## 1. 목적 및 운용 원칙

이 템플릿의 핵심 목적은 인프라 구축을 표준화하여 파편화를 방지하고, 보안과 모니터링이 기본 적용된 환경(Secure by Default)을 신속하게 프로비저닝하는 것입니다.

- **인프라 표준화**: 네트워크, 클러스터, 컨테이너 구성 양식을 통일하여 프로젝트 간 구성 오류(Configuration Drift)를 방지합니다.
- **무상태성 및 격리**: 모든 서비스는 컨테이너 기반으로 구동되며, 서비스 간 데이터 의존성은 API 및 메시지 큐로만 제한합니다.
- **보안 가이드라인 준수**: 민감 정보(Secret)의 코드 내 하드코딩을 금지하며, 외부 시크릿 관리 시스템 또는 암호화 매니페스트 사용을 강제합니다.
- **가시성 확보**: 이 템플릿으로 배포되는 모든 서비스는 별도 수동 설정 없이 중앙 모니터링 및 로그 수집 시스템에 자동 등록됩니다.

## 2. MSA 인프라 아키텍처 구조

```
외부 트래픽 요청
        │
        ▼
┌───────────────────────────────────────────────────┐
│  API Gateway Layer        (api-gateway/)          │
│  단일 진입점 제어, JWT 인증/인가, Rate Limiting    │
└──────────────────────┬────────────────────────────┘
                       │
                       ▼
┌───────────────────────────────────────────────────┐
│  Service Mesh Layer       (service-mesh/)         │
│  서비스 간 통신 암호화(mTLS), 트래픽 제어          │
│                                                   │
│   ┌─────────────┐          ┌─────────────┐        │
│   │  Service A  │  ◄─────► │  Service B  │  ...  │
│   └──────┬──────┘          └──────┬──────┘        │
└──────────┼───────────────────────┼────────────────┘
           │                       │
           ▼                       ▼
┌───────────────────────────────────────────────────┐
│  Data Layer               (terraform/ 으로 프로비저닝)│
│  서비스별 독립 DB (Database per Service 패턴)      │
│                                                   │
│   ┌─────────────┐          ┌─────────────┐        │
│   │ Database A  │          │   Redis B   │        │
│   └─────────────┘          └─────────────┘        │
└───────────────────────────────────────────────────┘

공통 관리 레이어
  ├── 컨테이너 인프라:  docker/  →  kubernetes/  →  helm/
  ├── 코드 기반 인프라: terraform/, ansible/
  ├── 시크릿 관리:      vault/, sealed-secrets/
  ├── CI/CD 파이프라인: jenkins/, github-actions/
  └── GitOps CD:        argocd/
  ├── DB 커넥션 풀링:   db-proxy/  (PgBouncer, ProxySQL)
  └── 비동기 메시징:    message-broker/  (Kafka, RabbitMQ)

운영 가시성 레이어 (Observability)
  ├── 모니터링 및 알림: monitoring/  (Prometheus, Grafana)
  └── 로그 중앙화:      logging/     (ELK, Loki)
```

## 3. 폴더별 상세 역할

### CI/CD — 지속적 통합 및 배포

> 코드 변경이 발생했을 때 자동으로 빌드 → 테스트 → 배포까지 이어지는 파이프라인을 정의합니다.
> 사람이 직접 서버에 접속해서 배포하는 방식을 없애고, 코드 변경만으로 배포가 트리거되도록 합니다.

| 폴더 | 도구 | 역할 |
|---|---|---|
| `jenkins/` | Jenkins | 온프레미스·폐쇄망 환경에서 주로 사용하는 CI/CD 서버. 방화벽 안쪽 사내망에 직접 설치해서 운영합니다. Declarative Pipeline 문법으로 빌드 → 테스트 → Docker 이미지 빌드 → 배포 흐름을 코드로 정의합니다. |
| `github-actions/` | GitHub Actions | GitHub 저장소에 내장된 CI/CD. 별도 서버 없이 PR을 올리거나 main에 머지하는 이벤트만으로 파이프라인이 실행됩니다. 컨테이너 이미지 빌드 후 레지스트리에 푸시하거나, 취약점 스캔(Trivy 등)을 자동 실행하는 워크플로우 템플릿을 담습니다. |
| `argocd/` | ArgoCD | GitOps 방식의 K8s 전용 CD 도구. Jenkins/GitHub Actions가 이미지를 빌드해서 레지스트리에 올리면, ArgoCD가 Git 저장소의 매니페스트 변경을 감지하고 자동으로 클러스터에 동기화합니다. "Git에 있는 상태 = 클러스터 실제 상태"를 보장하며, 누군가 클러스터를 직접 수정해도 Git 기준으로 자동 복구(Auto-sync)합니다. 멀티 클러스터 배포, 롤백, 배포 승인 게이트 설정 템플릿을 담습니다. |

---

### Container & Orchestration — 컨테이너 실행 및 관리

> 애플리케이션을 컨테이너로 패키징하고, 수십~수백 개의 컨테이너를 자동으로 관리하는 환경을 구성합니다.
> MSA에서는 서비스 수가 많기 때문에 수동으로 서버를 관리하는 것이 사실상 불가능합니다.

| 폴더 | 도구 | 역할 |
|---|---|---|
| `docker/` | Docker | 서비스별 `Dockerfile` 및 로컬 개발용 `docker-compose.yml` 템플릿. 이미지 크기를 줄이는 멀티스테이지 빌드 패턴과, 보안을 위해 root가 아닌 일반 계정으로 프로세스를 실행하는 설정을 기본 포함합니다. |
| `kubernetes/` | Kubernetes (K8s) | 수많은 컨테이너를 자동으로 배포·복구·스케일링해주는 오케스트레이션 시스템. 서비스가 죽으면 자동 재시작, 트래픽이 몰리면 자동으로 인스턴스를 늘려줍니다. Deployment, Service, Ingress, ConfigMap 등 핵심 매니페스트 템플릿을 담습니다. |
| `helm/` | Helm | Kubernetes 리소스를 하나의 패키지(Chart)로 묶어 관리하는 도구. 개발/스테이징/운영 환경마다 다른 설정값(이미지 태그, 리소스 크기, 도메인 등)을 `values.yaml` 파일 하나로 분리해서 관리합니다. |

---

### IaC & Configuration — 코드 기반 인프라 및 서버 설정

> 서버, 네트워크, 클러스터를 클릭이 아닌 코드로 만들고 관리합니다.
> 코드로 관리하면 Git에 이력이 남고, 동일한 환경을 언제든 재현할 수 있습니다.

| 폴더 | 도구 | 역할 |
|---|---|---|
| `terraform/` | Terraform | AWS, GCP, Azure 같은 클라우드 리소스(VPC, 서브넷, 보안그룹, K8s 클러스터, DB 인스턴스)를 코드로 선언하고 생성합니다. "이 코드 상태 = 실제 인프라 상태"가 되도록 관리합니다. |
| `ansible/` | Ansible | 이미 만들어진 서버에 접속해서 패키지 설치, 설정 파일 배포, OS 보안 설정 등을 자동화합니다. Terraform이 서버를 "만드는" 역할이라면, Ansible은 만들어진 서버를 "세팅하는" 역할입니다. |

---

### Security — 시크릿 및 보안 관리

> DB 패스워드, API 키, 인증서 같은 민감 정보를 코드나 Git에 평문으로 올리지 않고 안전하게 관리합니다.
> MSA 환경에서는 수십 개의 서비스가 각각 자격 증명을 필요로 하기 때문에, 중앙화된 시크릿 관리가 필수입니다.

| 폴더 | 도구 | 역할 |
|---|---|---|
| `vault/` | HashiCorp Vault | 시크릿 전용 저장소. 애플리케이션이 시작할 때 Vault에서 DB 패스워드나 API 키를 동적으로 발급받아 사용합니다. 시크릿이 만료되면 자동 교체되고, 누가 어떤 시크릿에 접근했는지 감사 로그가 남습니다. |
| `sealed-secrets/` | Bitnami Sealed Secrets | Kubernetes Secret을 암호화해서 Git에 안전하게 커밋할 수 있게 해주는 도구. 공개키로 암호화된 `SealedSecret` 파일은 클러스터 내부에서만 복호화 가능하므로, 외부에 노출되어도 안전합니다. |

---

### Proxy & Gateway — 트래픽 진입 및 라우팅

> 외부에서 들어오는 요청이 올바른 서비스로 전달되도록 제어합니다.
> MSA에서는 수십 개의 서비스가 있기 때문에, 클라이언트가 각 서비스의 주소를 직접 알 필요 없이 하나의 진입점으로 통합합니다.

| 폴더 | 도구 | 역할 |
|---|---|---|
| `nginx/` | Nginx | 가장 앞단에서 요청을 받아 내부 서비스로 전달하는 리버스 프록시. HTTPS 인증서 처리(SSL 종료), 정적 파일 서빙, 기본적인 로드밸런싱을 담당합니다. |
| `was/` | Tomcat, JBoss | Java 기반 웹 애플리케이션을 실행하는 WAS(Web Application Server) 설정 템플릿. 컨테이너 전환 전 레거시 환경이나 온프레미스 환경에서 사용합니다. |
| `api-gateway/` | Kong, Traefik | MSA의 단일 진입점. URL 기반으로 어떤 요청을 어떤 서비스로 보낼지 라우팅하고, JWT 토큰 검증, Rate Limiting(초당 요청 수 제한), 공통 인증 처리를 한 곳에서 수행합니다. |

---

### Service Mesh — 서비스 간 통신 관리

> 서비스 A가 서비스 B를 호출할 때 발생하는 모든 문제(암호화, 장애 전파, 지연 등)를 애플리케이션 코드 변경 없이 인프라 레벨에서 해결합니다.
> MSA에서 서비스가 많아질수록 서비스 간 통신 관리가 복잡해지는데, 이를 자동화해주는 레이어입니다.

| 폴더 | 도구 | 역할 |
|---|---|---|
| `service-mesh/` | Istio, Linkerd | 각 서비스 옆에 작은 프록시(사이드카)를 붙여서 모든 서비스 간 통신을 제어합니다. 통신을 자동으로 암호화(mTLS)하고, 특정 서비스가 과부하 상태일 때 요청을 차단하는 서킷브레이커, 트래픽의 일부만 새 버전으로 보내는 카나리 배포를 코드 없이 구현합니다. |

---

### DB Proxy — 데이터베이스 커넥션 풀링

> MSA에서는 서비스 수십 개가 각각 DB에 직접 커넥션을 맺으면 DB의 최대 커넥션 수가 금방 고갈됩니다.
> DB 앞단에 프록시를 두어 커넥션을 재사용(풀링)함으로써 DB 부하를 줄이고 안정성을 높입니다.

| 폴더 | 도구 | 역할 |
|---|---|---|
| `db-proxy/` | PgBouncer, ProxySQL | PgBouncer는 PostgreSQL 전용 커넥션 풀러입니다. 100개의 서비스가 DB에 붙더라도 실제 DB에는 10개의 커넥션만 유지하고 나머지는 풀에서 재사용합니다. ProxySQL은 MySQL 계열의 동일한 역할을 하며, 추가로 읽기/쓰기 분리(Read Replica 라우팅) 기능도 제공합니다. |

---

### Message Broker — 비동기 메시지 큐

> 서비스 A가 서비스 B를 직접 HTTP로 호출하면 B가 느려지거나 죽었을 때 A도 함께 영향을 받습니다.
> 메시지 브로커를 사이에 두면 A는 메시지만 던지고 끝내고, B는 자기 속도에 맞게 처리합니다. 서비스 간 결합도를 낮추는 MSA의 핵심 비동기 통신 패턴입니다.

| 폴더 | 도구 | 역할 |
|---|---|---|
| `message-broker/` | Kafka, RabbitMQ | Kafka는 대용량 이벤트 스트리밍에 적합합니다. 주문 생성, 결제 완료 같은 이벤트를 발행하면 여러 서비스가 동시에 구독해서 처리할 수 있습니다. RabbitMQ는 복잡한 라우팅과 작업 큐(Task Queue)에 적합하며, 메시지 처리 실패 시 재시도(Dead Letter Queue) 설정 템플릿을 담습니다. |

---

### Observability — 모니터링 및 로그 관리

> 수십 개의 서비스가 분산되어 있을 때, "지금 시스템이 정상인가?", "장애가 어디서 발생했는가?"를 빠르게 파악합니다.
> MSA에서 장애는 여러 서비스를 거쳐 전파되기 때문에, 중앙에서 전체를 한눈에 볼 수 있는 관찰 환경이 없으면 원인 파악이 매우 어렵습니다.

| 폴더 | 도구 | 역할 |
|---|---|---|
| `monitoring/` | Prometheus, Grafana | Prometheus가 각 서비스의 메트릭(CPU, 메모리, 응답시간, 에러율 등)을 주기적으로 수집하고, Grafana가 이를 시각화합니다. 특정 수치가 임계값을 초과하면 Slack, 이메일 등으로 알림을 보내는 Alert 설정 템플릿을 포함합니다. |
| `logging/` | ELK Stack, Loki | 각 서비스에서 출력되는 로그를 한 곳에 모아 검색하고 분석합니다. 분산된 서비스에서 동일한 요청을 추적하기 위해 Trace ID 기반 로그 검색 설정을 포함합니다. ELK(Elasticsearch + Logstash + Kibana) 또는 경량 스택인 Loki + Grafana 구성 템플릿을 담습니다. |

## 4. 구성 순서 (프로비저닝 파이프라인)

신규 환경을 처음부터 구축할 때 의존성을 고려하여 아래 순서로 진행합니다.

```
1. terraform/         클라우드 리소스 생성 (네트워크, 클러스터, DB 인스턴스)
        │
2. ansible/           생성된 서버 초기 설정 (OS 보안, 패키지 설치)
        │
3. vault/             시크릿 저장소 구축 및 자격 증명 사전 등록
   sealed-secrets/
        │
4. docker/            서비스 컨테이너 이미지 빌드
        │
5. kubernetes/        클러스터 핵심 오브젝트 배포
   helm/
        │
6. api-gateway/       외부 트래픽 진입점 및 라우팅 설정
        │
7. service-mesh/      서비스 간 통신 보안 및 트래픽 제어 적용
        │
8. nginx/             최외곽 프록시 및 도메인·인증서 연동
        │
9. db-proxy/          DB 앞단 커넥션 풀러 배포 (PgBouncer, ProxySQL)
   message-broker/   비동기 메시징 인프라 구성 (Kafka, RabbitMQ)
        │
10. jenkins/          CI 파이프라인 연동 (빌드, 테스트, 이미지 푸시)
    github-actions/
        │
11. argocd/           GitOps CD 연동 (Git 변경 감지 → K8s 자동 배포)
        │
12. monitoring/       메트릭 수집 및 알림 등록
    logging/          분산 로그 수집기 가동
```
