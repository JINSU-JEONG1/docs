이 문서는 인메모리 데이터 저장소를 처음 사용하는 팀원이 기본 개념과 사용 원칙을 빠르게 이해하기 위한 안내서입니다. 제품에 공통으로 적용할 원칙을 먼저 설명하고, 접속과 명령어는 팀에서 사용하는 Valkey를 기준으로 다룹니다.

## 1. 인메모리 데이터 저장소란

인메모리 데이터 저장소는 처리할 데이터를 주로 메모리에 두어 빠르게 읽고 씁니다. 디스크 중심 저장소보다 낮은 지연 시간을 기대할 수 있지만, 사용할 수 있는 메모리가 제한되어 있고 만료나 퇴거로 데이터가 사라질 수 있습니다.

제품과 설정에 따라 데이터를 디스크에 저장하거나 복제할 수 있지만, 애플리케이션은 필요한 키가 항상 존재한다고 가정하지 않습니다. 캐시 미스, 세션 만료, 장애 상황을 정상적인 흐름으로 처리해야 합니다.

## 2. 팀에서 사용하는 범위

팀에서는 인메모리 데이터 저장소를 캐시와 MSA 공용 세션에 사용합니다.

| 구분 | 캐시 | 세션 |
|---|---|---|
| 목적 | 반복 조회 비용을 줄입니다 | 여러 애플리케이션 인스턴스가 로그인 상태를 공유합니다 |
| 원본 | DB나 외부 시스템에 원본이 있습니다 | 인증 과정에서 생성한 상태를 보관합니다 |
| 데이터가 없을 때 | 원본에서 다시 조회할 수 있습니다 | 세션 만료 또는 미인증 상태로 처리합니다 |
| 만료 기준 | 데이터 특성과 허용 가능한 지연에 맞춥니다 | 로그인 정책과 보안 정책에 맞춥니다 |
| 삭제 시점 | 원본 변경, 명시적 무효화, TTL 만료 시점입니다 | 로그아웃, 강제 종료, TTL 만료 시점입니다 |

> **주의:** 캐시와 세션은 손실 영향이 다릅니다. 같은 만료 시간과 장애 대응 방식을 일괄 적용하지 않습니다.

이 문서는 다음 내용을 다룹니다.

- 인메모리 데이터 저장소의 기본 특성
- 캐시와 세션의 차이
- Valkey 접속과 기본 명령어
- 키 이름과 만료 시간 원칙
- 운영 환경에서 지켜야 할 안전 수칙
- 자주 발생하는 문제의 확인 방법

설치, 서버 튜닝, 클러스터, Sentinel, Lua, Pub/Sub, 분산 락, 큐, 요청 제한은 다루지 않습니다.

## 3. Redis와 Valkey

> **결론:** Redis와 Valkey는 뿌리와 기본 사용법이 같지만, 현재는 별도로 개발되는 제품입니다. 공통 명령은 비슷해도 최신 기능과 운영 조건이 항상 같다고 가정하지 않습니다.

Valkey는 Redis OSS 7.2.4를 기반으로 시작했습니다. Redis OSS 7.2 이하와 프로토콜, 설정, RDB·AOF 형식이 호환되며 기존 Redis 클라이언트도 연결할 수 있습니다. 분기 이후에는 두 제품이 독립적으로 기능을 추가하고 있습니다. 자세한 호환 범위는 [Valkey 마이그레이션 문서](https://valkey.io/topics/migration/)에서 확인합니다.

| 구분 | Redis | Valkey |
|---|---|---|
| 출발점 | 원래 Redis 프로젝트 | Redis OSS 7.2.4에서 분기 |
| 운영 주체 | Redis Ltd. 중심 | Linux Foundation의 개방형 거버넌스 |
| 라이선스 | 버전에 따라 다름 | BSD 3-Clause |
| 기본 명령 | `GET`, `SET`, `EXPIRE` 등 | 기본 범위에서 대부분 동일 |
| CLI | `redis-cli` | `valkey-cli` |
| 최신 기능 | Redis에서 독자적으로 개발 | Valkey에서 독자적으로 개발 |

Redis 7.2 이하는 BSD 3-Clause, Redis 7.4 계열은 RSALv2 또는 SSPLv1, Redis 8 이상은 AGPLv3·RSALv2·SSPLv1 중 하나를 적용합니다. Valkey는 BSD 3-Clause를 유지합니다. 라이선스 선택이나 배포 판단이 필요한 경우 [Redis 공식 라이선스 안내](https://redis.io/legal/licenses/)와 [Linux Foundation의 Valkey 소개](https://www.linuxfoundation.org/press/linux-foundation-launches-open-source-valkey-community)를 다시 확인합니다.

팀의 실제 사용 제품은 Valkey입니다. 따라서 이후 접속 방법, 명령 예시, 공식 문서 링크는 Valkey를 기준으로 합니다.

## 4. 접속 전에 확인할 정보

환경별로 다음 정보를 확인합니다.

- 호스트와 포트
- TLS 사용 여부
- ACL 사용자 이름
- 비밀번호를 가져올 비밀 관리 위치
- VPN 또는 사내망 연결 조건
- 개발·검증·운영 환경 구분

팀의 실제 접속 정보와 비밀 관리 위치는 [확인 필요]입니다. 비밀번호나 세션 식별자는 문서, 메신저, 이슈, 로그, 화면 캡처에 남기지 않습니다.

일반적인 접속 형태는 다음과 같습니다.

```shell
valkey-cli -h <host> -p <port> --tls --user <username> --askpass
```

TLS나 ACL을 사용하지 않는 환경이라면 해당 옵션을 제외합니다. 명령줄에 비밀번호를 직접 넣지 않습니다. 연결 옵션은 [Valkey CLI 문서](https://valkey.io/topics/cli/)를 따릅니다.

연결 후 응답을 확인합니다.

```text
PING
PONG
```

## 5. 키와 TTL

### 키와 값

Valkey는 키로 값을 찾습니다. 이 가이드의 캐시와 세션 예시는 문자열을 사용합니다.

- 문자열: 직렬화한 캐시나 세션을 하나의 값으로 저장할 때 사용합니다.
- 해시: 여러 필드를 한 키 아래에 저장할 때 사용합니다. 이 문서에서는 세션 만료를 한 번에 설정하기 위해 사용하지 않습니다.

자료형은 저장 구조와 접근 방식에 맞춰 선택합니다. 기존 키에 다른 자료형의 명령을 실행하면 `WRONGTYPE` 오류가 발생할 수 있습니다.

### TTL

TTL은 키가 자동으로 삭제되기까지 남은 시간입니다. 캐시와 세션 키에는 서비스 정책에 맞는 TTL을 둡니다. `SET` 명령의 `EX` 옵션은 초 단위 만료 시간을 함께 지정합니다. 기존 키를 `SET`으로 덮어쓰면 `KEEPTTL` 옵션을 사용하지 않는 한 이전 TTL이 사라집니다. `KEEPTTL`은 이미 설정된 TTL만 유지하며, TTL이 없는 키에 새 만료 시간을 만들지는 않습니다. 자세한 동작은 [`SET`](https://valkey.io/commands/set/), [`EXPIRE`](https://valkey.io/commands/expire/), [`TTL`](https://valkey.io/commands/ttl/) 문서를 참고합니다.

```text
SET guide:cache:user:42 '{"name":"sample"}' EX 300
TTL guide:cache:user:42
```

`TTL` 결과는 다음과 같이 해석합니다.

- 양수: 남은 만료 시간(초)입니다.
- `-1`: 키는 있지만 만료 시간이 없습니다.
- `-2`: 키가 없습니다.

### 만료, 퇴거, 영속성

세 개념은 서로 다릅니다.

- 만료(expiration): 설정한 TTL이 끝나 키가 제거됩니다.
- 퇴거(eviction): 메모리 한도에 도달했을 때 설정된 정책에 따라 키가 제거됩니다.
- 영속성(persistence): 메모리 데이터를 디스크에 기록해 재시작 후 복구할 수 있게 합니다.

Valkey는 여러 [퇴거 정책](https://valkey.io/topics/lru-cache/)과 [영속성 방식](https://valkey.io/topics/persistence/)을 제공합니다. 팀 환경에 적용된 정책은 [확인 필요]입니다.

## 6. 캐시 사용 원칙

> **결론:** 캐시는 원본을 대신하지 않습니다. 캐시가 없어도 원본에서 데이터를 다시 가져올 수 있어야 합니다.

기본 조회 흐름은 다음과 같습니다.

1. 정해진 키로 캐시를 조회합니다.
2. 값이 있으면 사용합니다.
3. 값이 없으면 DB나 외부 시스템에서 원본을 조회합니다.
4. 조회 결과를 TTL과 함께 캐시에 저장합니다.
5. 결과를 반환합니다.

원본 데이터가 변경되면 관련 캐시를 삭제하거나 갱신합니다. TTL은 데이터 변경 빈도, 최신성 요구, 원본 조회 비용을 함께 고려해 정합니다.

같은 시점에 많은 캐시가 만료되면 원본에 요청이 몰릴 수 있습니다. 대량으로 생성되는 캐시는 팀에서 정한 범위 안에서 TTL을 무작위로 분산합니다. 분산 범위는 서비스 특성과 부하 시험 결과에 따라 정하며 임의의 비율로 고정하지 않습니다.

원본에도 데이터가 없을 때 같은 조회가 반복된다면 짧은 TTL의 빈 값 캐싱을 검토합니다. 이때 실제 빈 값과 캐시 미스를 구분하고, 일시적인 원본 오류를 데이터 없음으로 캐시하지 않습니다.

캐시 장애 시 원본 조회로 우회할지, 요청을 실패시킬지는 서비스별로 [확인 필요]입니다. 우회를 허용하면 원본에 요청이 몰릴 수 있으므로 부하 한계도 함께 정해야 합니다.

## 7. 세션 사용 원칙

> **결론:** 클라이언트는 세션 식별자를 전달하고, 여러 MSA 인스턴스는 Valkey에 저장된 같은 세션 상태를 조회합니다.

일반적인 세션 흐름은 다음과 같습니다.

1. 인증이 성공하면 예측하기 어려운 세션 식별자를 생성합니다.
2. 세션 데이터를 Valkey에 TTL과 함께 저장합니다.
3. 클라이언트에는 세션 식별자만 안전한 방식으로 전달합니다.
4. 요청을 처리하는 인스턴스가 세션을 조회하고 인증 상태를 확인합니다.
5. 로그아웃하거나 세션을 강제로 종료할 때 키를 삭제합니다.
6. 키가 없거나 만료되었으면 미인증 또는 세션 만료로 처리합니다.

세션에는 필요한 정보만 저장합니다. 비밀번호, 원본 인증 토큰, 불필요한 개인정보를 넣지 않습니다. 세션 데이터 형식이 바뀔 수 있다면 버전 필드를 두고 이전 형식의 처리 방법을 정합니다.

다음 정책은 팀에서 [확인 필요]로 남아 있습니다.

- 세션의 절대 만료 시간
- 요청마다 만료 시간을 연장하는지 여부
- 동시 로그인 허용 범위
- 세션 데이터 형식과 필수 필드
- 세션을 만들고 수정하고 삭제할 수 있는 서비스
- Valkey 장애 시 인증 요청의 처리 방식

세션은 직렬화한 문자열과 TTL을 한 명령으로 저장합니다. `HSET` 후 `EXPIRE`를 따로 실행하면 두 명령 사이의 실패로 TTL 없는 세션이 남을 수 있습니다. 해시가 반드시 필요하다면 서버 버전과 클라이언트 기능을 확인한 뒤 트랜잭션이나 원자적 명령 사용 방식을 별도로 정합니다.

## 8. 클라이언트 장애 대응

> **주의:** 우회 정책이 있어도 클라이언트가 Valkey 응답을 오래 기다리면 애플리케이션 자원이 먼저 고갈될 수 있습니다.

애플리케이션은 연결과 명령 실행에 무제한으로 대기하지 않습니다. 다음 값을 서비스와 클라이언트 특성에 맞게 정합니다.

- 연결 타임아웃
- 명령 응답 타임아웃
- 재시도할 오류와 최대 횟수
- 연결 관리 또는 커넥션 풀 기준
- 캐시와 세션 각각의 실패 처리 방식

재시도는 부하를 늘리고 쓰기 명령을 중복 실행할 수 있습니다. 모든 오류와 명령을 일괄 재시도하지 않습니다.

## 9. 키 이름 원칙

키만 보고 용도와 소유 서비스를 구분할 수 있어야 합니다. 키에는 비밀번호, 토큰, 이메일, 전화번호 같은 민감한 값을 넣지 않습니다.

다음은 형식을 설명하기 위한 예시이며 팀 표준은 [확인 필요]입니다.

```text
cache:v<schema-version>:<service>:<resource>:<identifier>
session:<session-id>
```

캐시 키의 스키마 버전은 직렬화 형식이나 의미가 바뀔 때 이전 데이터와 새 데이터를 구분합니다. 버전 변경 후 남은 이전 키는 TTL로 자연스럽게 제거하거나 승인된 절차로 정리합니다.

환경은 서버나 논리적 저장 공간으로 분리하는 편이 우선입니다. 키에 환경을 넣어야 한다면 팀 전체가 같은 위치와 표현을 사용합니다.

아래 키와 값은 연습용입니다. 실제 운영 데이터로 그대로 실행하지 않습니다.

### 문자열 캐시

```text
SET guide:cache:user:42 '{"name":"sample"}' EX 300
GET guide:cache:user:42
EXISTS guide:cache:user:42
TTL guide:cache:user:42
TYPE guide:cache:user:42
DEL guide:cache:user:42
```

### 문자열 세션

```text
SET guide:session:sample '{"userId":"42","role":"member","version":1}' EX 1800
GET guide:session:sample
TTL guide:session:sample
DEL guide:session:sample
```

### 제한적으로 키 찾기

```text
SCAN 0 MATCH 'guide:*' COUNT 100
```

`SCAN`은 한 번의 호출로 모든 결과를 보장하지 않습니다. 반환된 커서가 `0`이 될 때까지 반복합니다. 전체 순회 비용은 키 수에 비례하고 `MATCH` 필터도 키를 가져온 뒤 적용되므로, 패턴 탐색을 운영 환경의 상시 조회 수단으로 사용하지 않습니다. 자세한 동작은 [`SCAN` 문서](https://valkey.io/commands/scan/)에서 확인합니다.

## 11. 운영 환경 안전 수칙

> **주의:** 운영 환경에서는 조회 명령도 부하를 만들 수 있습니다. 실행 전 환경, 키 패턴, 대상 수, 명령의 영향을 확인합니다.

- 전체 키를 한 번에 조회하는 `KEYS *`를 사용하지 않습니다. 필요한 범위를 `SCAN`으로 나눠 확인하되 전체 순회를 반복하지 않습니다.
- `FLUSHALL`과 `FLUSHDB`를 실행하지 않습니다. `FLUSHALL`은 모든 데이터베이스의 키를 삭제하는 위험 명령입니다. 자세한 내용은 [`FLUSHALL` 문서](https://valkey.io/commands/flushall/)를 참고합니다.
- 운영 환경에서 `MONITOR`를 실행하지 않습니다. 모든 명령을 스트리밍하므로 서버 처리량을 크게 떨어뜨릴 수 있습니다. 자세한 내용은 [`MONITOR` 문서](https://valkey.io/commands/monitor/)를 참고합니다.
- 와일드카드를 이용한 일괄 삭제를 하지 않습니다.
- 쓰기나 삭제 전 현재 접속한 환경을 다시 확인합니다.
- 큰 컬렉션이나 삭제 비용을 알 수 없는 키는 운영 정책을 확인하고, 허용된 경우 `DEL` 대신 메모리를 비동기로 회수하는 [`UNLINK`](https://valkey.io/commands/unlink/)를 사용합니다.
- TTL이 필요한 키를 만료 시간 없이 저장하지 않습니다.
- `CONFIG`, 디버그 명령, 서버 전체에 영향을 주는 변경은 운영 담당자의 승인 없이 실행하지 않습니다.
- Valkey를 인터넷에 직접 노출하지 않습니다. 네트워크 제한, ACL, TLS 등 팀 보안 구성을 따릅니다. Valkey의 기본 보안 전제와 기능은 [보안 문서](https://valkey.io/docs/topics/security/)와 [TLS 문서](https://valkey.io/topics/tls/)에서 확인할 수 있습니다.

## 12. 문제를 만났을 때

| 증상 | 먼저 확인할 내용 |
|---|---|
| 연결할 수 없음 | 호스트, 포트, VPN·사내망, 방화벽, TLS 사용 여부 |
| `NOAUTH` 또는 `WRONGPASS` | ACL 사용자, 비밀번호, 비밀 관리 위치, 계정 권한 |
| 조회 결과가 없음 | 키 이름, 환경, `EXISTS`, `TTL` 결과가 `-2`인지 확인 |
| `TTL`이 `-1` | 만료 시간 없이 저장된 이유와 의도 여부 확인 |
| `WRONGTYPE` | `TYPE <key>`로 실제 자료형 확인 |
| 메모리 또는 쓰기 오류 | 메모리 한도와 퇴거 정책을 운영 담당자에게 확인 |
| 세션이 예상보다 일찍 끝남 | 세션 TTL, 연장 방식, 퇴거 여부, 강제 종료 이력 확인 |

원인을 확인할 때 실제 비밀번호, 세션 식별자, 개인정보를 공유하지 않습니다. 재현에 필요한 경우 개발 환경의 가짜 데이터를 사용합니다.

## 13. 팀에서 확정할 항목

> **결정:** 아래 항목이 정해지면 이 문서의 예시와 운영 절차를 팀 표준으로 바꿉니다.

- 환경별 접속 주소와 네트워크 조건
- TLS와 ACL 적용 방식
- 비밀번호를 가져올 비밀 관리 위치
- 키 이름 규칙과 서비스별 소유 범위
- 데이터 유형별 캐시 TTL
- 캐시 TTL 분산 범위와 빈 값 캐싱 기준
- 세션 TTL과 연장 방식
- 세션 직렬화 형식과 버전 관리 방법
- 연결·명령 타임아웃, 재시도, 연결 관리 기준
- 영속성과 퇴거 정책
- 캐시·세션 장애 시 서비스 동작
- 모니터링 화면, 알림 기준, 운영 문의처

## 14. 빠른 확인

| 확인할 것 | 명령 또는 기준 |

| 연결 상태 | `PING` → `PONG` |
